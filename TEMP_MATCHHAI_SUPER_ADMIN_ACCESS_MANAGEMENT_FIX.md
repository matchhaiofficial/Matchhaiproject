## 1. Current access model (after fix)

Super Admin access = **DB role `super_admin` (canonical) / `super-admin` (legacy, read-only)** **OR** **active env-allowlist email**. The **backend is the sole authority**; the client only routes.

All three server gates now resolve through ONE shared module — `convex/superAdminAccess.ts`:

| Gate | File | Entry | Resolver |
|---|---|---|---|
| Session-token admin dashboard | `convex/admin.ts` `getAuthenticatedAdmin` | `isAuthorizedSuperAdmin` | shared |
| Identity (`ctx.auth`) paths | `convex/authz.ts` `requireSuperAdmin` | `isSuperAdminProfile` → `isAuthorizedSuperAdmin` | shared |
| Support-knowledge admin | `convex/supportKnowledge.ts` | `isSuperAdminProfile` → `isAuthorizedSuperAdmin` | shared |
| Client routing/guard (hint only) | `src/utils/accountRouting.ts`, `app/super-admin/_layout.tsx` | `isSuperAdminProfile(user)` | role-first, env fallback |

## 4. Centralized helper summary (`convex/superAdminAccess.ts`)

- `SUPER_ADMIN_ROLE = "super_admin"`, `LEGACY_SUPER_ADMIN_ROLE = "super-admin"`.
- `isSuperAdminRole(role)` accepts both (read compat); writes use canonical only.
- `getSuperAdminAllowlist()` = **union superset** so no gate loses a prior access path: named server slots `SUPER_ADMIN_EMAIL_<NAME>`, `SUPER_ADMIN_ALLOWLIST_JSON`, primary `SUPER_ADMIN_EMAIL`/`EXPO_PUBLIC_SUPER_ADMIN_EMAIL`, and `EXPO_PUBLIC_SUPER_ADMIN_EMAILS` (CSV).
- `isAuthorizedSuperAdmin(profile,email)` = role OR active allowlist email. **No hardcoded fallback** (fail closed).
- `resolveSuperAdminAccessSource` → `db_role | env_allowlist | both | null` (overview only).

## 5. Grant/revoke mutation summary

**`admin.grantSuperAdmin({ sessionToken, targetUserId?|targetEmail?, reason? })`**
- Caller must be an authenticated Super Admin (`getAuthenticatedAdmin`); actor never from client input → **no self-promotion** (a non-admin can't call it; an admin granting self is a no-op).
- Target resolved by id or **normalized exact email**; must already exist (never creates accounts/passwords).
- Sets canonical `super_admin`; normalizes legacy `super-admin` → canonical. Idempotent.
- Fires `account.role_changed` notification + audit log (`grant_super_admin` / `normalize_super_admin_role`).

**`admin.revokeSuperAdmin({ sessionToken, targetUserId?|targetEmail?, reason? })`**
- Caller must be an authenticated Super Admin.
- **Self-revoke blocked** (another Super Admin must do it).
- **Last-admin lockout protection**: blocks if it would leave 0 DB-role admins **and** 0 active env-allowlist entries.
- Env-allowlisted target with no DB role → explained, not silently failed (must remove env to revoke).
- Clears `role`; fires notification + audit log (`revoke_super_admin`).

## 6. Access overview query summary

**`admin.listSuperAdminAccess({ sessionToken })`** (Super Admin only). Returns safe fields only — no hashes/tokens/secrets:
- `dbRoleAdmins[]`: userId, fullName, email, role, isCanonicalRole/isLegacyRole, accountType, accountStatus, createdAt, lastActiveAt, source.
- `envAllowlistAdmins[]`: displayName, email, source, hasMatchingAccount, userId?, accountStatus?, lastActiveAt?.
- `summary`: counts (dbRole, canonical, legacy, envAllowlist, envAllowlistOnly).
- Purpose: confirm whether **Ovais** and the five partners hold DB-role access, and who is env-only.

## 7. Client route guard changes

- `isSuperAdminProfile(user)` checks **DB role first** and returns immediately — a DB-role Super Admin routes correctly with **no `EXPO_PUBLIC` env and no app rebuild**.
- Env email/id remain a **fallback hint only**; comments state the backend re-checks every call.
- `app/super-admin/_layout.tsx` unchanged (already consumes this helper + redirects non-admins).

## 8. Audit logging behavior

- New actions in `superAdminAuditLogs` (module `access`): `grant_super_admin`, `revoke_super_admin`, `normalize_super_admin_role`.
- Each row: actor (super-admin id/name/email), target (`targetType:"user"`, `targetId`, `targetEmail`), status, optional reason, safe metadata (previousRole/newRole, remaining-admin counts). Metadata passes through `sanitizeAuditMetadata`.

## 9. How to add five partner Super Admins safely (preferred: DB role)

1. Each partner **registers normally** (own email + password). **Do not create passwords for them.**
2. An existing Super Admin calls **`admin.grantSuperAdmin`** with the partner's email (or via a future UI).
3. Backend sets canonical `super_admin` and audit-logs it.
4. Partner logs in → client routes to Super Admin (DB role) → **no env change, no app rebuild**.
5. Every Super Admin API call is re-verified server-side.
6. Verify with `admin.listSuperAdminAccess`.

_Alternative (env allowlist):_ set `SUPER_ADMIN_EMAIL_<NAME>` in the Convex dashboard **and** `EXPO_PUBLIC_SUPER_ADMIN_EMAIL_<NAME>` in the app build env, then rebuild. Less preferred (two targets + rebuild).
